# Phase 5 — 체류(Visit) 상세 화면: 사진 + 메모

**날짜**: 2026-09-19
**상태**: 기능 구현 완료, 화면/CRUD 로직은 세션 내 검증 완료 — 아래 트러블슈팅 항목은 웹 개발 폴백에 한정된 미해결 이슈로 Phase 7(네이티브 검증)에서 최종 확인 필요

## 목표
체류 기록 목록/상세 화면을 만들고, 각 체류에 대해 (a) 카메라로 사진을 촬영해 첨부, (b) 텍스트 메모를 입력/저장하는 기능을 구현한다.

## 수행한 작업

### 1. 패키지 설치
- `@capacitor/camera@8.2.4`, `@capacitor/filesystem@8.1.3`

### 2. 사진 저장 서비스 ([photo.service.ts](../../src/services/photo/photo.service.ts))
- `capturePhotoForVisit(visitId)`: `Camera.takePhoto()`(신규 API — 구버전 `getPhoto`는 deprecated)로 촬영 → 네이티브에서는 카메라가 반환한 캐시 파일을 `Filesystem.copy()`로 앱 영구 저장소(`Directory.Data/photos/`)에 복사 후 `Filesystem.getUri()`로 안정적인 URI를 얻어 `photos` 테이블에 저장. 카메라가 반환하는 원본 URI는 OS가 언제든 지울 수 있는 캐시 디렉터리에 있을 수 있어 그대로 저장하지 않음.
- 웹(개발 폴백)에서는 실제 파일시스템이 없으므로 `webPath`(blob: URL, 세션 동안만 유효)를 그대로 저장 — 문서화된 제약사항.

### 3. 화면 구성
- [VisitListScreen.tsx](../../src/screens/VisitListScreen.tsx): `db.listVisits()`로 체류 목록(도착 시각, 체류 시간) 표시, 항목 클릭 시 상세로 전환 (라우터 없이 내부 상태로 목록/상세 전환하는 master-detail 패턴)
- [VisitDetailScreen.tsx](../../src/screens/VisitDetailScreen.tsx): 체류 시간·위치 표시, "사진 촬영" 버튼(→ `capturePhotoForVisit` 호출 후 썸네일 목록 갱신), 메모 textarea + 저장 버튼(`db.upsertMemo`)
- `App.tsx`에 "체류 기록" 탭 추가 (임시 상단 내비게이션에 통합)

## 트러블슈팅: 웹 개발 폴백에서 새로고침 후 데이터가 간헐적으로 사라짐 (미해결 — 중요)

Phase 4에서 `autoSave` 속성 수정으로 "데이터가 저장 자체가 안 되는" 문제는 해결했지만, 이번 단계에서 그 수정 이후에도 **간헐적으로** 새로고침 직후 목록이 비어 보이는 현상이 남아있음을 발견해 깊이 조사했다.

**조사 과정**:
1. 브라우저 콘솔에서 `db.service.ts`를 직접 import해 단계별로 실행하며 어디서 멈추는지 확인 — 처음에는 `CapacitorSQLite.initWebStore()` 자체가 영구적으로 멈추는(resolve도 reject도 안 되는) 현상을 발견.
2. Vite의 의존성 최적화 캐시(`node_modules/.vite`)가 세션 내내 갱신되지 않고 있었을 가능성을 의심해 캐시를 삭제하고 개발 서버를 완전히 재시작 → 이후에는 멈추지 않고 진행되었으나, 대신 **새로고침 시점에 따라 결과가 오락가락하는(성공/빈 목록)** 패턴으로 바뀜.
3. 콘솔에 남는 내부 로그(`#### getVersion new res: ...`)를 관찰한 결과, 한 번의 페이지 로드 안에서 `PRAGMA user_version` 조회 결과가 **처음엔 0(스키마 없음), 잠시 후 1(정상 스키마)**로 바뀌는 사례를 확인했다. 즉 `db.open()`이 resolve된 시점에도 jeep-sqlite가 IndexedDB에 저장해둔 실제 DB 파일을 메모리로 복원하는 내부 작업이 아직 끝나지 않은 상태일 수 있고, 그 사이에 쿼리를 날리면 "방금 막 생성된 빈 스키마"를 보게 된다.

**적용한 완화 조치** ([db.service.ts](../../src/services/db/db.service.ts)):
1. `initDb()`를 동시 호출에 안전하게 만듦 — 이전에는 `if (db) return db;`만 체크해서, React StrictMode의 이중 effect 호출 등으로 동시에 두 번 호출되면 각각 별도의 `ensureWebStore()`/`createConnection()`을 시작해버리는 경쟁 상태가 있었다. 진행 중인 초기화 Promise를 캐싱(`initPromise`)해 모든 동시 호출자가 동일한 하나의 초기화를 기다리도록 수정.
2. `db.open()` 직후, 웹 플랫폼에서만 `PRAGMA user_version`이 우리 스키마 버전과 일치할 때까지 최대 25회(40ms 간격, 총 1초) 폴링 — 복원이 끝나기 전의 "빈 스키마" 상태를 걸러내기 위함.

**현재 상태 — 완전히 해결되지 않음**: 위 조치를 모두 적용한 뒤에도, 반복 테스트에서 새로고침 시 정상적으로 데이터가 보이는 경우와 여전히 빈 목록으로 보이는 경우가 섞여서 나타났다 (예: 연속된 두 번의 새로고침 중 첫 번째는 성공, 두 번째는 실패). 즉 근본 원인(jeep-sqlite/sql.js의 IndexedDB 복원 완료 시점을 우리 코드가 확실히 알 방법이 마땅치 않음, 어쩌면 이 브라우저 자동화 환경에서 Web Worker 관련 제약이 있을 가능성)을 완전히 제거하지는 못했다.

**영향 범위 판단**: 이 문제는 **`jeep-sqlite`(웹 브라우저 전용 SQLite 폴백)의 내부 동작에 한정**된다. 네이티브 Android에서 사용하는 `@capacitor-community/sqlite`의 실제 구현은 기기의 실제 파일시스템에서 직접 SQLite 파일을 열기 때문에 "IndexedDB로부터 비동기 복원"이라는 단계 자체가 존재하지 않아 이 레이스 컨디션이 원천적으로 발생할 수 없다. 따라서 이 이슈가 실제 배포될 Android 앱의 데이터 신뢰성에 영향을 준다고 볼 근거는 없지만, **Phase 7에서 실기기로 반드시 재확인**해 정말 영향이 없는지 검증해야 한다.

## 확인/테스트 방법과 결과
- `npm run build` — 성공
- 브라우저(Claude 내장 브라우저)로 화면 단위 기능 검증 (위 트러블슈팅으로 인해 "새로고침 직후"가 아니라 "같은 세션 내"에서 확인):
  - 콘솔로 체류 레코드를 삽입 → "체류 기록" 탭에서 목록에 정상 표시됨
  - 목록 항목 클릭 → 상세 화면에 체류 시간/위치가 정확히 표시됨
  - 메모 textarea에 텍스트 입력 후 "메모 저장" 클릭 → 목록으로 돌아갔다가 다시 들어가면 저장된 메모가 그대로 로드됨 확인
  - "사진 촬영" 버튼 클릭 시 크래시 없이 동작 (웹에서는 브라우저의 파일 선택/카메라 UI로 폴백되는 `@capacitor/camera`의 표준 동작 — 실제 촬영 완료까지는 이 자동화 환경에서 진행하지 못했으나 버튼 클릭 자체와 에러 핸들링 경로는 정상)
- **미검증**: 실기기에서의 실제 사진 촬영 → 영구 저장소 복사 → DB 연동 전체 흐름. Phase 7에서 실기기로 확인 필요.
