# 22. 버그 수정: "81시간" 표시 오류 + 종료되지 않은 추적 기록 복구

## 증상

사용자가 "오늘 사용했는데 시간이 81시간이 되는 게 있다"고 리포트. 실기기 DB를 직접 꺼내 분석.

## 분석

| 항목 | 값 |
|---|---|
| 경로 ID 127 | 09:04:35 시작 → 10:26:34 종료 |
| 실제 저장된 GPS 포인트 | 921개, 09:04:36 ~ 10:26:28 (스팬 4912초) |
| `duration_sec` | 4918 (= 1시간 21분 58초) |
| 화면 표시 | "이동 시간 : **81:58**" |

데이터 자체(거리 3.56km, 포인트 921개, 스팬 4912초)는 정확했다. 문제는 `formatDurationClock()`(Phase 12에서 도입)이 "분:초"만 표시하고 60분이 넘어도 시간 단위로 올리지 않도록 설계되어 있었던 것 — 81분 58초가 그대로 "81:58"로 표시되어, 숫자만 보면 "81시간"처럼 보이는 심각한 오해를 유발했다.

같은 DB를 보던 중 별개의 문제도 발견: **`ended_at`이 NULL인 채로 영구히 남은 경로가 3건** (9/23, 9/24, 그리고 리포트 시점 기준 당일 10/17). 앱이 백그라운드에서 강제 종료되거나 스와이프로 종료되는 등 "추적 중지" 버튼을 누를 기회 없이 트래킹이 중단되면, `routes` 테이블의 해당 행은 이름·거리·시간이 영원히 비워진 채 남고, 재실행 후에는 `isTracking()`이 항상 `false`로 리셋되기 때문에 UI에서 이 기록을 다시 "종료"할 방법이 없었다.

## 수정

### 1. 시:분:초 표시
`src/utils/datetime.ts`의 `formatDurationClock()`을 60분 이상이면 자동으로 "H:MM:SS" 형식("1:21:58")으로, 미만이면 기존처럼 "MM:SS"로 표시하도록 수정.

### 2. 종료되지 않은 추적 기록 자동 복구
- `db.service.ts`에 `listOrphanedRoutes()` 추가 — `ended_at IS NULL`인 경로 조회.
- `geolocation.service.ts`에 `recoverOrphanedRoutes()` 추가 — 각 미종료 경로에 대해, 저장된 `track_points`의 마지막 타임스탬프를 종료 시각으로, 실제 기록된 포인트 간 haversine 거리 합을 이동 거리로 계산해 `endRoute`/`setRouteName`/`updateRouteStats`로 정상 마감. 포인트가 하나도 없으면 시작 시각 = 종료 시각(거리 0)으로 마감.
- `App.tsx`에서 앱 시작 시 `db.initDb()` 직후 한 번 호출. 이 시점엔 아직 사용자가 "추적 시작"을 누르기 전이므로(이 모듈의 메모리 상태는 항상 "추적 꺼짐"으로 새로 시작), `ended_at IS NULL`인 행을 전부 "방치된 것"으로 간주해도 안전하다.

## 검증

실기기에서 앱을 완전히 재시작(강제 종료 후 재실행)한 뒤 확인:
- 기존에 이름이 비어 있던 미종료 경로 3건(9/23, 9/24, 10/17) 모두 정상적인 "YYYY-MM-DD HH:mm:ss" 이름을 갖게 됨 — 복구 로직이 정상 작동.
- 문제의 경로(09:04:35 시작, 3.56km)를 열어 "이동 시간"이 **"1:21:58"**로 정상 표시됨을 확인.
